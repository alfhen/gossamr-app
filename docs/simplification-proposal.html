Gossamr · design proposal

Gossamr, simplified

Pip drives everything. Workstreams are the only container. Agents are plain Claude Code sessions with your own config, plus one MCP server so they can report back. Every write Gossamr makes to Jira or GitHub is still a draft you approve.

1Summary

Gossamr today is about 207,000 tracked lines, counting code, tests, fixtures and e2e. It was built around an idea the owner no longer wants: the app polices the agents. Today it has:

  • four separate mode systems;
  • about 40 settings;
  • about ten ways to start an agent;
  • six auto-start rules, with per-workstream overrides;
  • budgets, holds and tripwires;
  • a read-only permission regime, a permission-prompt classifier and a preflight checklist.

A TypeScript copy of most of these rules is kept in step with the Rust through 10,000 lines of shared fixtures.

This proposal cuts Gossamr down to four concepts and one loop:

Pip

The only driver. You talk to Pip. Pip sees every workstream and agent, starts and steers agents, and drafts every update Gossamr makes to Jira and GitHub.

Workstreams

The only container: one ticket (or one ticketless question), with its agents, drafts and Pip conversation.

Agents

Plain claude --bg --worktree sessions with your own Claude config. Gossamr adds one MCP server to each, so the agent can report back, ask Pip a question and read its workstream.

Drafts

The one gate that stays. Every write Gossamr makes to Jira or GitHub is a draft you approve with one key. Agents push their own branches and open draft PRs with their own git and gh.

What that adds up to:

  • one mode: Pip manages;
  • one way to start work: ask Pip;
  • one result channel: the agent's report call, with the transcript as a fallback;
  • one draft card;
  • one status word per workstream.

About 40% of the codebase goes. Section 9 has the per-area figures, and some of them are estimates.

Pip runs as claude -p with every built-in tool off, no user settings, and only the gossamr MCP server. It can read and draft, but it can never touch files, a shell or the network.

Agents run as claude --bg --worktree in a clone of the repo. Gossamr reads their state by polling claude agents --json. Their results come from an opt-in report_result tool on a second MCP server, or, more often, from parsing headings such as For Jira: and Verdict: out of the final answer.

The ways to start an agent today are:

  • the palette, two ways;
  • the ticket menu;
  • the Agents button;
  • Build-from-plan;
  • Review-this;
  • retry;
  • the Pip StartRun card;
  • inline start;
  • suggestion chips;

Nearly all of it exists to stop an agent or Pip from doing something without your say-so. The vision turns that around. You drive by talking to Pip. Claude Code's own harness polices the agents. Gossamr guards only its own writes to Jira and GitHub.

The loop

There is no rule table. When an agent finishes, Gossamr wakes Pip in that workstream with the facts: ids, role, state, and whether the agent reported. Pip reads the report and decides what to do next. It might:

  • start a reviewer;
  • send the builder a fix;
  • draft the Jira comment;
  • ask you.

Pip follows your instruction for that workstream. If you say "Plan and build CA-412, have it reviewed", that is the authority for Pip to start a planner, then a builder, then a reviewer, without asking again for each one.

Roles are labels, not tiers

Pip picks the role (planner, builder, triager, reviewer, investigator, or anything else) and writes the brief. These all go:

  • the six fixed templates;
  • the per-kind required fields, such as plan_from_run, build_account and findings_from_run;
  • the per-kind permission profiles.

Gossamr still wraps Pip's text in one base brief, because some facts only Gossamr can get right:

  • Checkout. A worktree starts at the clone's current HEAD, not at the base branch (domain/run.rs:738). So the base brief always says to run git fetch origin <base> and switch to that branch before starting.
  • Pull requests. When Pip passes a PR, start_agent checks that it comes from the same repository (CodeChange::is_same_repo) and pins its head SHA. The base brief then says to:
    • fetch pull/<n>/head;
    • check out <sha> detached;
    • stop if that fails, rather than review the base branch instead.
  • Data. The ticket text is fenced off as data. One sentence explains how to use report, ask and read_workstream.

A handoff is a report that the next agent reads with read_workstream. It is no longer a typed slot that Core fills in.

set_view_filter and the pip-view event go. Pip tells you where to look instead of moving the page.

  • resolves the clone and the base branch;
  • generates the worktree name itself. The role is a short label, checked for length and characters, and used only in the session name;
  • records which Pip turn started the agent.

The reminder prefix (runs/answer.rs:20) stays, because the original brief drops out of a long conversation.

What stays locked on Pip

Pip keeps its current boundary:

  • no built-in tools;
  • no user settings;
  • only the gossamr MCP server;
  • reads only watched projects and repos, and the tickets you handed it.

Pip reads untrusted ticket and PR text all day, and it can now start agents, so this boundary matters more than before. Pip does not need a shell: when code needs reading or changing, it starts an agent.

Pip keeps an explicit model setting. It runs with --setting-sources "", so it never reads your default model (Decision 6).

Wakes

The supervisor shrinks to a waker.

What wakes Pip. An agent in a workstream changes to done, failed or needs-you, or is stopped by something other than Gossamr, Pip or you. The stop-then-resume inside message_agent wakes nobody. Nor does a stop that you or Pip asked for.

At most once. Each (agent, state) pair still wakes Pip at most once. The pair is recorded in the workstream's audit log, as it is today, and a restart rebuilds the list from that log. Without it, the 30-second sweep would wake Pip again for the same finished run. A waiting wake merges with any newer one, and your own messages go ahead of waiting wakes.

What a wake contains. Only facts Gossamr wrote. Pip reads the agent's own words with read_agent.

What goes.

  • the Advise/Manage gate;
  • the auto-start pass and the fix-round cap;
  • budgets and "Allow 5 more";
  • the six hold reasons and four tripwires;
  • the SupervisorCore, CoreFacade and WakeQueue traits.

Backstops. Three remain, and none of them is a setting:

  • the global cap on agents running at once;
  • a limit on wakes per workstream per day;
  • a limit on Pip turns per day across all workstreams.

The two daily limits are fixed in code. When one is hit, the workstream pauses (one paused_reason column) and you are told. A Resume control on the workstream clears the pause. A loop that goes wrong then costs money once, not all night.

When the app is closed. Pip runs as a claude -p process started by the app, so it does not run while the app is closed. Agents keep running in Claude's daemon. At the next launch, recover() brings Gossamr's records in line with the agents, and the waker sends Pip the state changes it missed.

One prompt

The Assistant/Manager split goes. One short system prompt says:

  • who Pip is and what it can see;
  • that ticket and agent text is data, not instructions;
  • that Gossamr's writes to Jira and GitHub are drafts;
  • that Pip tells you whenever it starts an agent from a wake turn.

Each tool description shrinks to one sentence.

5Agents on the Claude Code harness

Launch

claude --bg --name "Gossamr: CA-412 builder" --worktree <slug> \
       --mcp-config <app data>/agents/<agent id>.json \
       --allowedTools mcp__gossamr__report,mcp__gossamr__ask,mcp__gossamr__read_workstream,mcp__gossamr__read_ticket \
       --append-system-prompt <base brief> -- <Pip's brief>

The agent runs with your own permission mode, settings, hooks, CLAUDE.md, MCP servers and model. The only allow rule Gossamr adds is for its own four tools, so a call to report never turns into a permission prompt. --allowedTools works together with --bg, and resuming the session in place keeps it (docs/agents-cli-findings.md:147).

goes These go:

  • the read-only regime: dontAsk mode, empty --setting-sources, --strict-mcp-config, the exact allow list and the deny list of about 60 rules;
  • the pushing switch;
  • the per-kind lockdowns.

stays These stay, because the harness needs them and each was checked against the real CLI (docs/agents-cli-findings.md):

  • Shell environment. Gossamr captures your login-shell environment once, because an app launched from the Dock doesn't see your PATH. The shared --bg daemon takes its environment from the first launch.
  • Token file. The MCP address and token go in a per-agent config file that only you can read (0600). The daemon is shared, so an environment variable set at launch can't reach the session.
  • Resume. Use claude --bg --resume <session id> -- <message> with no other flag, at least 5 s after stop, and check the id that comes back. Any extra flag, or a resume that comes too soon, starts a copy of the session.
  • Untrusted folders. Gossamr detects Workspace not trusted at launch and offers Open in Terminal, which runs claude in the clone so you can accept Claude's own trust prompt. The pre-check that reads .claude.json goes, along with the amber preflight row.
  • Refused permission modes. --bg refuses to launch in auto mode unless you have opted in, or in bypassPermissions mode unless you have accepted it. The launch then fails with Claude's own message and the same Terminal fix.
  • Cleanup and git. claude rm is never forced. Gossamr's own git calls run with hooks off, a timeout and no prompts.
  • Finding a clone. Gossamr looks in ~/Code, ~/Developer and ~/src for a clone whose origin matches the repo. If it finds several or none, you pick one, or click Clone it on the workstream. Pip can't choose a clone path.

The agent's side of the MCP server

The second server, run-report, merges into the single gossamr server. The merged server keeps what lets run-report survive app restarts, which the current gossamr server lacks: today it binds port 0 and keeps its tokens in memory (agent/mcp.rs:94-110). The merged server has:

  • a remembered port that it binds again at each start;
  • agent tokens stored as hashes in the account database, revoked when the agent reaches done, failed or stopped;
  • two kinds of token. Pip's token lasts one turn and reaches Pip's tools. An agent's token reaches only that agent's four tools.
Agent toolPurpose
report(status, summary, body?, reviewed_sha?)status is done, blocked or question. summary is one line. body is Markdown: a plan, findings, or a review with file:line references. A reviewer passes the SHA it reviewed.
ask(question)Waits a fixed time for Pip, or you through Pip, to answer. If the time runs out, it tells the agent to end its turn with the question, and the answer arrives later by resume.
read_workstream()The ticket text, Pip's notes, and the reports of earlier agents in the workstream. This is how a builder reads the plan, and how a reviewer reads the builder's account.
read_ticket(key)Cached text of a linked ticket, fenced off as data

The report stays in its own run_reports table. The tracker rewrites a run's record on every poll, so a report stored there could be lost (db/schema.rs:216-218).

The heading parser goes (runs/result.rs, 1,138 lines). If an agent ends without calling report, its last message in the transcript becomes the summary, and Pip is told the agent didn't report. That fallback is the second result channel.

Agent tokens keep well-behaved agents in their lane. They are not a security boundary. Agents run as the same macOS user, so an agent can read other agents' config files, the account database, and Pip's token from Pip's process. Section 10 covers what that means.

Permission prompts and questions

Nothing outside a --bg session can answer its permission prompt. --permission-prompt-tool works only with --print, which --bg rejects. Any flag on resume starts a copy of the session.

  • Permission prompt. The agent shows as needs-you, with the command Claude asked about. One button, Open in Terminal, runs claude attach <id> so you can answer Claude's own prompt.
    • Gossamr keeps the choice between Terminal and iTerm for this button.
    • These go: the classifier in runs/permission.rs with its TypeScript copy and fixtures, Allow-once-in-Terminal with its explainer, and deny-by-stop-and-resume.
  • Question. The agent calls ask. Pip answers from what it knows, or calls ask_person. If the answer comes quickly, the agent carries on in the same turn. If not, it ends its turn with the question, and message_agent resumes it later.

If you want fewer prompts, change your own Claude Code default mode. Gossamr adds no setting for this.

States

All ten stored run states stay:

  • recover() uses Launching to adopt or fail a run after a restart (runs/service.rs:630-640).
  • Unknown marks a session that has been lost.

The UI shows six:

  • queued;
  • working, which covers launching too;
  • needs you;
  • done;
  • failed, which covers unknown once the recovery window has passed;
  • stopped.

The mapping from claude agents --json (runs/state.rs) stays. It has been checked against the real CLI, and it is the only source of truth for state.

6Drafts: the one gate

8Backend surface after

Commands

About 35 commands, down from 142:

  • auth and connections;
  • cache reads, activity and sync;
  • the watch list;
  • drafts: list, edit, approve, skip;
  • Pip: ask, cancel, turns;
  • workstreams: list, read, close, reopen, resume, choose clone, clone;
  • agents: list, read, stop, stop all, open in Terminal, clean up, archive;
  • settings.

Events

Four events, down from 11:

  • changed { topic } replaces the seven events that carry only a connection id;
  • the streamed pip event;
  • snapshot, which drives the Dock badge;
  • open-run, which brings the window forward when you click a notification.

Data

  • runs: today runs.proposal_id is NOT NULL with a unique index, and that index is what stops a run launching twice (db/schema.rs:189-205). One migration rebuilds the table with:
    • a nullable proposal_id;
    • a unique start_key;
    • kind replaced by role;
    • the removed fields dropped from the data JSON.
  • Removed enum variants: stored drafts with removed intents are retired. Old RunKind values stay readable as serde aliases that map to role labels.
  • workstreams: loses the mode, rules, budget and spend columns. One paused_reason column stays.
  • run_reports: stays as its own table and gains reviewed_sha.
  • Migrations: the 13 existing steps stay, and new steps are added after them.

Abstractions removed

  • AgentProvider, AgentCaps and the 2,262-line conformance suite, which serve a single provider;
  • the unused AuthMethod variants;
  • the SupervisorCore traits;
  • the unused WorkTracker and CodeHost methods behind #![allow(dead_code)].

Kept, and opened up for Linear

The WorkTracker trait stays, with three changes:

  • its Jira-only parts (Scope { cloud_id }, Connection::jira(), and the CachedTicket dispatch with its unreachable! arms) move into the Jira adapter;
  • Gossamr's internal intents come out of the tracker's write type;
  • each signed-in account keeps its own database. A Linear connection adds one more database, and Pip reads across all of them.

10What we give up

  1. The draft gate covers only Gossamr's own writes.

    Agents now run with your own tools. A builder pushes branches and opens PRs with git and gh. An agent that has your Atlassian or GitHub MCP servers could write to Jira or GitHub directly. The brief tells agents to report to Gossamr instead, but that is a request, not a lock. Decision 2 settles whether agents get your MCP servers at all.

  2. Agents are no longer kept read-only.

    A planner or reviewer could write if its brief, or text injected into a ticket, told it to. Today dontAsk mode and empty setting sources block that. What still limits the damage:

    • ticket text stays fenced off as data;
    • every agent works in its own worktree;
    • a reviewer's brief says to change nothing.
  3. Push and PR rules become requests.

    Today, in a mode that asks for permission, Gossamr's classifier refuses:

    • a push to anything but the agent's own branch;
    • a PR that is not a draft;
    • gh pr merge.

    After this change they are instructions in the brief. In a mode that asks, Claude Code's own prompt still catches them. In bypassPermissions mode, nothing does.

  4. Reviewing a PR runs that PR's Claude config.

    When a reviewer checks out a PR branch, it loads that branch's .claude/settings.json hooks and its CLAUDE.md, with your permissions. Today's empty setting sources prevent that. The same-repo rule stays, so a PR from a fork is never checked out. A teammate's branch, though, gets the same trust as your own repo.

  5. Pip can start agents on its own judgement, even in a wake turn while you are away.

    Text injected into a ticket could try to talk Pip into starting an agent with a hostile brief. What still limits it:

    • Pip treats ticket and agent text as data;
    • Pip tells you whenever it starts an agent in a wake turn;
    • those starts show at once on the Work screen, with Stop;
    • the daily limits pause a workstream that runs away;
    • Pip itself has no file, shell or network access.

    None of these is a lock.

  6. Agent tokens don't separate local processes.

    Agents run as the same macOS user. A hostile agent could:

    • read other agents' token files and the account database;
    • take Pip's token for the current turn from the process list (ps eww), then call start_agent or draft with it until the turn ends.

    What still holds:

    • a draft still needs your key;
    • Pip's tokens are revoked when each turn ends;
    • Gossamr treats its database as readable by any agent.
  7. Chains depend on Pip's judgement, not rules.

    The fixed table (Investigate → Triage → Plan → Build → Review) always fired the same way. Pip may skip or reorder steps. That is the point, but a weak Pip turn can stall a workstream. The safety net is the wake on every state change, plus the "Pip asks you" item.

  8. Cost is only loosely bounded.

    The fixed daily limits cap wakes and Pip turns. Nothing caps a single long agent. It runs until it finishes, until you stop it, or until Claude's own limits stop it.

  9. Permission prompts still need Terminal.

    The current Claude Code CLI gives Gossamr no way to answer a prompt from inside the app.

11What we keep on purpose

  • The draft gate. Every write Gossamr makes to Jira or GitHub is a draft you approve. One executor applies it. Rewrites keep the basis check, and reviews keep the check before posting.
  • Secrets. They live only in the Keychain, in one item that is read once.
  • The MCP server. It listens only on the local machine and checks every request. It binds a stable port and revokes agent tokens by agent state.
    • Tokens are issued per session, compared in constant time, and stored as hashes.
    • Requests must pass Host and Origin checks.
  • Untrusted text. Ticket, PR and agent text is fenced off as data and cleaned before it is stored, shown or given to a model. Cleaning strips control, bidi and markup characters and redacts secrets.
  • Pip's lockdown. Pip has no built-in tools.
  • The wake ledger. Each (agent, state) pair wakes Pip at most once, across restarts.
  • One launch per start key. The same start can't launch twice.
  • PR checkouts. The same-repo check runs before a PR checkout, and the head SHA is pinned when the agent starts.
  • Jira sessions. The scope check runs before every Jira request (SiteChanged). The single refresh lock stays for Atlassian tokens, which change at every refresh.
  • Folder trust. Gossamr detects an untrusted folder, and you answer in Claude's own prompt.
  • Cleanup and git. claude rm is never forced, and Gossamr's git calls run with hooks off.
  • Recovery. The stored run states that recover() needs after a restart stay.
  • Harness knowledge. The checked CLI facts in docs/agents-cli-findings.md stay, with the captured CLI fixtures that pin them.

13Decisions for the owner

  1. Approval for Jira and GitHub writes

    Recommended: keep approval per draft, one key each.

    The alternative is that Pip applies a write after you say yes in chat. That removes the card, but leaves a model to decide what your "yes" means.

  2. Agents' MCP servers

    Recommended: agents get your own MCP servers, as any Claude Code session would, and their brief sends Jira and GitHub updates through Gossamr.

    This is also how Pip reaches tools beyond Jira and GitHub, such as Slack or Confluence: it starts an agent that has them.

    The alternative is --strict-mcp-config with only the gossamr server:

    • The draft gate then covers everything except git and gh.
    • Agents lose your other tools.

  3. Pip's own lockdown

    Recommended: keep it: no built-in tools, only MCP.

  4. Unrestricted agents

    Recommended: yes, accepting items 2 to 4 in Section 10. Even so, never recommend bypassPermissions.

  5. Screens

    Recommended: keep Inbox, Board and List. Remove Map, Age, "What Jira saw" and the PR viewer.

  6. Pip's model

    Recommended: keep an explicit model setting for Pip.

    Pip reads none of your settings, so it can only follow your default model if Gossamr reads that one value and passes it as --model.

  7. Atlassian sign-in

    3LO sign-in needs a client secret (auth/atlassian.rs:1). A bundled client means shipping a secret that can be extracted, and using one Atlassian app for everyone.

    Recommended: bundle the client for internal builds, and keep the setup screen for everyone else.

14Spikes before step 3

  1. MCP allow rule. Does --allowedTools mcp__gossamr__… stop permission prompts for the four agent tools under each mode you might use: default, acceptEdits and auto?
  2. Resume keeps the MCP config. Does a --bg --resume with no flags keep the --mcp-config?
  3. Reconnect after restart. After the app restarts on the same port, does a running session reconnect? Or does its next tool call fail, and if so, does a resume fix it?
  4. Tool-call timeout. How long will Claude Code wait on an MCP tool call before giving up? The answer sets the ask timeout.
  5. Resume copies. With the 5 s wait and the id check, how often does a resume still start a copy? If it never does, runs/continuation.rs can go with nothing to replace it.
