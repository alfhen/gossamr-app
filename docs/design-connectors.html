Design proposal · Draft for discussion · 29 Sep 2026

A connector-based work aide

Turn Jira Inbox, now called Gossamr, into a general aide for developers and PMs. Jira, GitHub and, later, Linear become connectors. The app owns one normalised model of work, and Pip, the built-in assistant, helps by proposing changes that you approve.

Names. Gossamr is the product. Pip is the assistant you talk to and who acts in the app. Claude is the default model behind Pip, reached today through Claude Code and a local MCP server. The provider is pluggable: other agents such as Codex can sit behind Pip later (section 10). This document says "Pip" when it describes what the assistant does, and "Claude" only where it means the model or the integration.

1. Why now, and what we are not doing

The prototype (prototype/claude-companion.html) shows what the product wants to be: one workspace across projects with a board, map, list and age view. Pip follows what you are looking at, drafts changes, and can follow GitHub and Jira activity on your behalf. None of those screens needs to know it is Jira underneath. Building them on the current code would bake Jira into places that are expensive to change later.

Goals

  • One domain model that every screen, and Pip, uses. Connectors translate to and from it.
  • Jira and GitHub first. Adding a third connector (Linear is the test case) should not change the core.
  • Pip never writes to a system by itself. Every change is a proposal that a person approves.
  • A pluggable assistant provider: Claude by default, others (such as Codex) later, all behind the same tools and the same approval flow.
  • Local-first: a local cache is the source for the UI, and the app stays fast offline.

Non-goals

  • A dynamic plugin system. Connectors are compiled in for now.
  • A lowest-common-denominator model. Connector-specific data stays available next to the normalised fields.
  • Cloud sync of drafts between devices, or a server that receives webhooks. See the risks section.

2. Where the code is today

About 3,900 lines of Rust in src-tauri/src. It works well as a Jira client, and Jira is visible in these places:

Two things are already in good shape: the frontend talks to the backend through an interface with a mock behind it (src/backend/), and the "the assistant can only propose" rule is already enforced in the MCP server. Both carry over.

3. Principles

  1. The app owns the model. Connectors translate at the edge. Nothing above the connector layer sees ADF, JQL or a transition id.
  2. Capabilities, not assumptions. Each connector declares what it supports. The UI adapts. It does not check "is this Jira".
  3. One write path. Every change to an external system is an approved proposal executed by a connector. Nothing else writes.
  4. Rules decide, Pip words. Deterministic rules decide whether something should be proposed. Pip (through Claude) writes the text. That keeps autopilot predictable, cheap and testable.
  5. Generalise on the second implementation. Design the domain now. Shape the traits against two real APIs, not one plus a guess.

4. Architecture

Suggested crate split, once the boundaries have settled: domain (types, filter, reconcile), core (cache, sync, proposals, autopilot), one crate per connector, and the Tauri app with the Pip bridge. A single crate with modules is fine until Phase 3.

6. Connector traits

Small traits per role. A connector implements the ones it can. GitHub is a CodeHost and an EventSource. Jira and Linear are WorkTrackers and EventSources.

#[async_trait]
pub trait WorkTracker: Send + Sync {
    fn capabilities(&self) -> TrackerCaps;
    fn key_pattern(&self) -> &Regex;                        // ENG-123, PROJ-45
    async fn sync(&self, since: Cursor) -> Result<Delta<WorkItem>>;
    async fn workflow(&self, c: &ContainerRef) -> Result<Workflow>;
    async fn people(&self, q: &PersonQuery) -> Result<Vec<Person>>;
    async fn apply(&self, intent: &Intent) -> Result<Applied>;    // the only write path
    fn compile(&self, f: &Filter) -> Option<NativeQuery>;      // optional server-side narrowing
}

pub trait CodeHost: Send + Sync {
    async fn sync(&self, since: Cursor) -> Result<Delta<CodeChange>>;
    async fn comment(&self, change: &CodeRef, body: &Doc) -> Result<()>;   // later, and proposal-gated too
}

pub trait EventSource: Send + Sync {
    async fn poll(&self, cursor: Cursor) -> Result<(Vec<Event>, Cursor)>;
}

pub struct TrackerCaps {
    pub subtasks: bool, pub mentions: bool, pub attachments: bool,
    pub transitions: TransitionModel,     // Graph | Any
    pub grouping: Grouping,               // Epics | Projects | Cycles | None
    pub custom_workflows: bool,
}

Capabilities drive the UI. If transitions is Any, the board allows any drop. If it is a graph, columns the card cannot reach dim during a drag, as they do in the prototype.

The one write path. apply(&Intent) is called by the approval layer and by nothing else. Pip's tools have no access to it.

7. Proposals and approval

A proposal is a neutral intent plus enough context to keep it honest.

enum Intent {
    Comment   { item: ItemRef, body: Doc },
    Transition{ item: ItemRef, to: StatusId },
    Create    { container: ContainerRef, fields: NewItem, link: Option<Link> },
    Update    { item: ItemRef, patch: Patch },        // triage: assignee, epic, priority
    Link      { from: ItemRef, to: ItemRef, kind: LinkKind },
    Subtasks  { parent: ItemRef, summaries: Vec<String> },
}

struct Proposal {
    id, created_at, origin: Origin,    // Chat | Board | Autopilot(event_id)
    intent: Intent,
    basis: Basis,                      // fingerprint of what it was drafted against
    state: Pending | Applied | Discarded | Superseded(reason),
    revisions: Vec<Revision>,
}

Keeping proposals current

Basis records what the proposal was drafted against: the item's status, comment count, assignee, epic and so on. "Keep drafts up to date" is then a pure function, reconcile(proposal, current cache) → Keep | Revise(note) | Retire(reason), run after every sync and every approval. It is easy to test and needs no model call. The prototype's cases:

  • A transition whose target status is already reached is retired. If the path changed, it is revised.
  • A reply draft is retired if the person withdrew the question or you already commented. It is extended, never silently rewritten, if a follow-up arrives.
  • A triage proposal drops fields that someone else already set, and is retired when none are left.

Bulk actions

Bulk approval covers transitions only, behind a confirmation that lists each move. Comments are never bulk-approved. Discarding is always safe and undoable.

8. Events and autopilot

Event kinds: CommentAdded, StatusChanged, Assigned, ItemCreated, PrOpened, PrMerged, CheckFailed, ReviewRequested. Connectors produce them, and autopilot only consumes them. That is why GitHub and Jira are symmetric.

fn on_event(ev: &Event, cache: &Cache, s: &AutopilotSettings) -> Vec<ProposalChange>

It is a pure function, so every rule is a unit test. The model is used only for wording, for example the body of a reply or the reason for a triage suggestion. Rules decide whether to act.

Rules that ship first

EventProposal
PR opened for an item you ownTransition to the container's review status, if the workflow has one and a path exists.
PR mergedTransition to Done, or the next status such as Testing, using the shortest workflow path.
Check failedDraft comment with the failing test, and flag the item as needing you.
Comment addedDraft reply, or extend an existing one.
Item created, unassignedTriage: assignee, epic, priority and a link if one is likely.
Review requested from youNo draft. The item moves into Needs me.
Blocker donePropose unblocking your own dependants.
Scope rule (decided). Autopilot drafts only for items assigned to you. The exceptions are a comment arriving on any item, a review requested from you, and brand-new unassigned items for triage. It never drafts updates on someone else's items otherwise. This is a fixed rule, not a setting. Everything else is opt-in: off by default, switched on per project, with each behaviour individually toggleable.

9. Filters as the query language

The prototype's filter chips are already a connector-neutral query language. Make that explicit:

enum Filter {
    NeedsMe, Mine, Unassigned, Blocked, Open,
    Assignee(PersonId), Status(String), Category(Category),
    Stale { days: u32 }, Container(ContainerRef), Parent(ItemRef),
    Text(String), Items(Vec<ItemRef>),          // Items is a "lens" Pip builds
    And(Vec<Filter>),
}

Views run the filter locally against the cache, so they are instant and identical for every connector. A connector may implement compile() to narrow what it fetches (JQL for Jira, GraphQL filters for Linear), but correctness never depends on it. Pip searches with the same Filter, so it never writes JQL. "Show what's blocked in webshop" becomes a filter, and the user can see and edit it as chips.

10. Pip and the assistant provider

The current design (a local MCP server, headless Claude Code, proposals only) stays as the default. Changes:

  • Connector-neutral tools. get_item, search_items(filter), list_next_statuses and the propose_* tools (comment, transition, create, update, subtasks).
  • Pip can see proposal state. A list_proposals tool returns what is pending, applied or superseded. The result of every propose_* call says exactly where the draft appears ("saved as a draft on ENG-491, shown in Activity and on that ticket"). Today the assistant guesses where a card shows up, and guesses wrong.
  • Screen context. Each turn carries what the user sees: view, filters, selected item, selected text. This is what powers the always-present avatar.
  • Provider-neutral tools. The tool surface is plain MCP, so any MCP-capable agent can use it. The provider layer is described at the end of this section.
  • Fresh sessions by default. A new session scoped to the item. Resuming an old session is opt-in and labelled with what it was about.
  • Untrusted input. Ticket and comment text is data, never instructions. Proposal-only writes are the main defence, and every proposal shows its source.

Providers: Claude by default, others pluggable

Claude is the default provider, not a hard-wired one. Pip's persona, tools, drafts and approval flow are the same whichever model sits behind it. Because Pip's tools are a local MCP server, any agent that speaks MCP can drive them. That gives two families of provider:

FamilyExamplesHow it runsTrade-offs
CLI agentsClaude Code (today), Codex CLI, Gemini CLI and similarThe app launches the user's installed agent headlessly with the user's own login, points it at our MCP server, and parses its output stream.Uses the person's existing subscription and can read the repo in the session's folder. Each CLI has its own flags, config, event format and session store, so each needs an adapter.
API providersAnthropic API, OpenAI API, local models through an OpenAI-compatible endpointThe app runs the tool loop itself against the same tool definitions.No repo access unless we add read-only file tools. Needs API keys in the keychain and cost tracking. Good for cheap background wording.
#[async_trait]
pub trait AgentProvider: Send + Sync {
    fn id(&self) -> &'static str;                        // "claude-code", "codex", "anthropic-api", ...
    fn capabilities(&self) -> AgentCaps;
    async fn detect(&self) -> Availability;               // installed? signed in? version?
    async fn run(&self, req: AgentRequest) -> Result<BoxStream<AgentEvent>>;
    async fn cancel(&self, run: &RunId);
    async fn sessions(&self, item: &ItemRef) -> Result<Vec<SessionInfo>>;   // for opt-in resume
}

struct AgentRequest {
    prompt: String, screen_context: Context, system: String,
    tools: McpEndpoint,                 // our local server, the only tool surface
    cwd: Option<PathBuf>, session: Option<SessionId>,
    task: Task,                         // Chat | Wording | Triage, so routing can pick a model
}
enum AgentEvent { Started { session }, Text(String), ToolUse { name, label }, Done { session, ok, message } }
struct AgentCaps { mcp: bool, resume: bool, streaming: bool, reads_code: bool, read_only_sandbox: bool, models: Vec<ModelInfo> }

Adapters translate to and from this shape. The event stream is already normalised in the current code (claude/stream.rs turns Claude Code's output into text, tool and done events), so the Claude Code adapter is mostly a move, not a rewrite. Tool labels already key off the tool's own name and ignore the provider's prefix (mcp__server__tool in Claude Code), which is the right habit.

The safety rule must hold for every provider

"Propose only" is enforced by our MCP server, but a CLI agent brings its own tools (shell, file edits). Each adapter therefore has to start its agent read-only and prove it. The two ignored tests in claude/mod.rs (a real run that proposes through the server, and a write probe) become a conformance suite that every provider must pass:

  1. It cannot write a file.
  2. It can call get_item and propose_comment, and the proposal reaches the app.
  3. It has no route to Jira or GitHub except through our tools.
  4. A run can be cancelled and leaves no process behind.
  5. A session can be resumed, or the provider says it cannot.

What I found for Codex (checked 29 Sep 2026)

  • codex exec runs Codex non-interactively. --json turns stdout into a JSONL event stream that includes MCP tool calls. The prompt can come from stdin (codex exec -).
  • The default sandbox is read-only. Writes need an explicit --sandbox workspace-write.
  • codex exec resume <SESSION_ID> continues a run. --ephemeral avoids persisting one. --ignore-user-config skips the user's config.toml, which helps isolate a run.
  • MCP servers are configured in config.toml (STDIO or HTTP transports). A server marked required makes codex exec fail if it cannot start.
  • Not confirmed: how to attach our per-run MCP endpoint without editing the user's own config. Options to test are a project-scoped .codex/config.toml or command-line config overrides. This is the main unknown for a Codex adapter.

Routing, privacy and settings

  • Per-task choice. Pip's chat, autopilot wording and triage rationale can use different providers or models. Because rules decide and the model only words, a cheaper or local model is enough for autopilot text.
  • Always visible. The chat header says "powered by" and names the provider. Ticket and comment text goes to whichever provider is selected, so the privacy note and settings must always show which one that is.
  • Organisation control. A configuration option lists the providers a workspace may use, so an organisation can restrict them.
  • Resume is provider-specific. Each provider lists its own resumable sessions. A fresh session scoped to the item stays the default.
  • Same persona, different behaviour. Models follow instructions differently. Keep the system prompt short and provider-neutral, and tune it per adapter only where a provider needs it.

Sources: Codex non-interactive mode (the older developers.openai.com/codex/noninteractive address redirects here). MCP configuration details come from a search summary of the Codex MCP docs, which I did not open directly.

11. Storage, sync and identity

Storage

SQLite. Every table is keyed by (connection_id, external_id): connections, containers, workflows, items, comments, links, code_changes, events, proposals, proposal_revisions and settings. Proposals are persisted, so a restart no longer loses drafts. Open question: one database per profile with a connection_id column, versus one per connection as today.

Sync

Polling with cursors. Jira keeps its updated-since approach. GitHub uses conditional requests (ETags) on the notifications and events APIs to stay inside rate limits. The existing wake notifier in Core becomes the scheduler's trigger, and each connector gets its own backoff and rate budget.

Identity

An Identity links a person's accounts across connections. "Me" is defined once, and rules like "assigned to me" use it. Linking a GitHub login to a Jira account is a one-time setup step, with a suggested match from email.

Secrets

Per-connection tokens stay in the OS keychain, as they are today. How people sign in, and what we have to register to let them, is section 12.

12. Authentication and distribution

Today each user registers their own Atlassian OAuth 2.0 (3LO) app and pastes in a client id and secret (auth.rs, save_oauth_app). That does not scale to other people. This section records what the providers actually allow, checked on 29 Sep 2026, and what we should do about it.

What the providers allow

ProviderFinding
Jira Cloud (Atlassian 3LO)
  • PKCE is only half supported. Atlassian's discovery document lists S256 as a supported code-challenge method, but its token endpoint accepts only client_secret_basic and client_secret_post. There is no "none" method, so every 3LO client is confidential and must send the client secret to exchange a code and to refresh a token. PKCE can strengthen the flow but cannot replace the secret.
  • The docs say 3LO supports only the authorization-code grant, and acknowledge this blocks standalone mobile and native apps. Refresh tokens rotate: each use invalidates the previous one, and a refresh also needs the secret.
  • An Atlassian staff reply (May 2024) confirms there is no public-client PKCE and suggests each customer register their own app, which is what we do today. A feature request for public-client PKCE (ECO-283, opened May 2024) was the tracking ticket in the sources I found. I could not confirm its current status.
  • Distribution is possible through the Developer Console's sharing settings. Users are then sent a direct authorisation link.
  • The discovery document also lists a device authorisation endpoint. One secondary source says the device grant is disabled for 3LO apps. I did not test it, so treat device flow as unavailable until proven.
GitHub
  • The device flow needs only the client id. The docs state the client secret is not needed. It must be switched on in the app's settings.
  • GitHub App user tokens expire after 8 hours, with a refresh token valid for 6 months. Refreshing normally needs the client secret, except for tokens that were issued through the device flow. So device flow gives us sign-in and refresh with no secret at all.
  • Limits to design for: 50 verification submissions per hour per app, and a minimum polling interval with slow_down back-off.
LinearNot investigated yet. It is part of Phase 5.

Decision (29 Sep 2026): option B for now. An admin registers one company-owned Atlassian app. People paste its client id and secret into the setup screen that already exists (the secret is shared through the team's password manager, not committed anywhere), then click "Sign in with Atlassian". No managed configuration and no server for the pilot. The audience is developers and technical people, so options A (own app) and D (API token) stay available for anyone who prefers them, and we will not build a polished onboarding flow yet. Option C (a token broker) is revisited only if the app is distributed outside the company before Atlassian supports public clients.

What the admin registers: an OAuth 2.0 (3LO) integration with the Jira API scopes read:jira-work, write:jira-work and read:jira-user (plus offline_access, requested by the app), and the callback URL http://localhost:8723/callback. The app needs no code change for this.

GitHub recommendation

Register one GitHub App owned by us, with the device flow enabled and narrow permissions. It needs read access to pull requests, checks and repository metadata. Later, PR comments would also be write-gated behind proposals. A GitHub App gives per-repo installation and lets an organisation admin approve it once, which is easier to defend than a broad OAuth scope. A fine-grained personal access token is the fallback. No user creates any app.

Design consequence

Authentication becomes part of the connector contract, so that adding a sign-in path never touches the core:

enum ClientSource { Bundled, ManagedConfig, UserSupplied }

enum AuthMethod {
    OAuthCode   { client: ClientSource, pkce: bool },   // Jira today: needs the secret
    DeviceFlow  { client_id: String },                  // GitHub: no secret
    ApiToken    { fields: Vec<TokenField> },            // Jira email+token, Data Center PAT
    Broker      { base_url: Url },                      // option C, later
}

#[async_trait]
pub trait Authenticator: Send + Sync {
    fn methods(&self) -> Vec<AuthMethod>;
    async fn begin(&self, m: &AuthMethod) -> Result<AuthChallenge>;   // URL, or user code plus URL
    async fn complete(&self, c: AuthChallenge) -> Result<Credentials>;
    async fn refresh(&self, cred: &Credentials) -> Result<Credentials>;
}
  • Credentials live in the keychain per Connection. Refresh tokens that rotate are written back before the old value is discarded.
  • Secrets and tokens are never logged (the existing redaction test is the pattern to keep), and sign-out revokes where the provider supports it.
  • The setup screen shows only the methods a connector offers, in order of preference.

Distribution checklist

  • Register the Atlassian app and set its distribution (needed for B and C). The vendor details Atlassian requires for sharing are still to be confirmed.
  • Register the GitHub App and enable device flow.
  • Sign and notarise the macOS build, and add an updater. Without notarisation, users see Gatekeeper warnings.
  • Have the AI policy and GDPR review done before anyone outside the pilot uses it (see section 15).

Sources: Atlassian OAuth 2.0 (3LO) apps, Atlassian developer community: PKCE thread, Atlassian OpenID configuration, GitHub: authorizing OAuth apps (device flow), GitHub: refreshing user access tokens.

13. The frontend contract

  • Types are generated from the Rust domain (for example with ts-rs or specta) instead of hand-mirrored in types.ts.
  • The store holds normalised entities. Board, Map, List, Age and Activity are pure functions of (items, workflows, filter, proposals).
  • Board columns come from the selected container's Workflow. With several containers selected the board falls back to the three categories.
  • The UI never sees ADF, JQL or transition ids. Capability flags arrive in the snapshot.
  • The mock connector replaces backend/mock.ts, so the same fixtures drive the UI in dev, tests and the browser.

14. Migration plan

Phase 0 · Domain and Jira adapter first

Extract the domain types. Put the existing Jira code behind WorkTracker. Replace Scope with Connection, and put sign-in behind the Authenticator trait (section 12). No visible change.

Done when: existing tests pass, Core holds a registry rather than a Jira, and no UI-facing code imports from jira.

Phase 1 · Persisted proposals

Proposals table and the approval executor. Chat cards read from it. Neutral MCP tools, including list_proposals. Extract an AgentProvider trait, with the current Claude Code integration as its first adapter. Reconcile as a pure function with tests.

Done when: drafts survive a restart, and approving one goes through apply and nothing else.

Phase 2 · Workspace UI

The prototype's board, map, list, age view, tabs, ⌘K, peek sheet, Pip pane with screen context, and draft cards. Built on the normalised store with the mock connector.

Done when: the Jira Inbox (Gossamr) screens are replaced and the app runs fully on the mock with no network.

Phase 3 · GitHub connector and events

CodeHost and EventSource for GitHub, signing in through the device flow with one GitHub App. Link discovery from PR titles and branches. Identity mapping. The Activity screen.

Done when: a real PR appears linked to its ticket and produces events.

Phase 4 · Autopilot

The rules engine, settings (opt-in, per project, per behaviour), reconcile on every sync, and the scope rule.

Done when: the seven rules in section 8 each have unit tests, and turning autopilot off produces zero proposals.

Phase 5 · Second tracker

Implement Linear (or GitHub Issues). Core changes are allowed only to fix real gaps, and each gap is written down.

Done when: the gap list is short and the UI needed no connector-specific branches.

Phase 6 · Second assistant provider

A Codex CLI adapter (or another provider), run through the conformance suite in section 10. Add the per-task provider setting.

Done when: Pip runs on the second provider with the same tools and the same approval flow, and the conformance suite passes for both.

Open questions

  • Is public-client PKCE (ECO-283) still open, and does the device grant work for our app type? Both would remove the shared secret and are worth re-checking before any distribution outside the company.
  • One database per profile, or per connection?
  • Can GitHub Issues act as a WorkTracker for repos that do not use Jira, and should it be the second tracker instead of Linear?
  • Do drafts need to follow you between devices, or is local-only enough?
  • Which second provider first: Codex CLI, or an API provider? Can we attach our MCP endpoint to Codex per run without touching the user's own config?
  • Should the organisation be able to restrict which providers are allowed?
  • Does reply wording come from the model on every event, or on demand when you open the draft, to control cost?
  • What is the product called, now that it is not only an inbox?
