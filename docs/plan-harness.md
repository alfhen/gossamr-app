# Plan: the harness

This plan builds [the harness proposal](harness-proposal.md). One orchestrating session runs it: for each step it starts a build session, then a verify session and a review session that know nothing of the build session's reasoning, and it merges the step into the integration branch `harness`. `main` changes only when the maintainer merges.

A first draft of this plan was reviewed adversarially by three readers, and its rewrite by a fourth. Their blockers are answered in the design (proposal section 10) and in the entries below.

## Goals this serves

- **Agents take a ticket from plan to pull request, and you only make the decisions.** Pipelines (H19 to H22) extend this from one ticket to a release.
- **Work with the tools you already use.** Gemini is added and a provider becomes a row (H6 to H13).
- A new goal, proposed in G0: **you set goals and gates for a repo, and Pip builds inside them.**
- Non-goals changed on the owner's instruction of 22 Nov 2026: "No sandbox or agent harness of its own", "No hosted service, for now", "macOS only, for now", and rule 1 for GitHub. G0 rewords them.
- Non-goals kept: no writes to Jira without a draft, not a replacement for the tracker, Pip stays locked down.

## How the build is run

1. **Build.** One session per step on Opus, in its own worktree, on a branch cut from `origin/harness`. Its brief is the entry below plus the findings it needs.
2. **Evals first.** Before writing code the build session writes the step's evals into the pull request: plain sentences, each with the command that checks it. They include every Acceptance line. Afterwards they may be added to, never weakened.
3. **Verify.** A second session, from a clean clone of the branch: runs the checks, runs every eval, removes the change to prove each regression test fails without it, and uses the feature the way a person would, on real providers where the entry says so.
4. **Review.** A third session, beside the second: reads the diff against the entry and the rules with the aim of refuting it. Findings are blocker, major or minor.
5. **Fix.** Blockers, majors and failed evals go back to the build session. Steps 3 to 5 repeat, at most four rounds. A step that does not converge is stopped and reported, not merged.
6. **Land.** The orchestrator squash-merges the pull request into `harness` when CI is green, verify passed, review has no blocker or major, and CodeRabbit's comments are answered. Minors become issues.
7. **After each wave** the orchestrator runs the full checks on `harness`.

Sessions that write the same files run one after the other.

## Rules for every step

- The app works after every step: it starts, signs in, shows tickets, Pip answers, and a Claude agent runs.
- Each step adds a regression test that fails when the change is removed.
- Tests never touch the real `~/.claude*`, `~/.codex`, `~/.gemini`, the Keychain or the real PATH. They use the fake CLIs in `src-tauri/test-support/` and the mock provider (H2).
- Real-provider checks are `#[ignore]` tests or scripts under `spikes/`, run by the verify session on the owner's logins, in a scratch repo under the session's temp folder with a local bare repo as its remote. Each proves afterwards that no process, worktree or scratch login is left.
- A real-provider script records each login's config files before and after (a hash of each config file, and only the size and modification time of a credential file) and fails when one changed. H0 found that `codex app-server` writes `~/.codex/config.toml` by itself.
- Every library or CLI API is checked against current documentation (a docs lookup tool first, where the session has one) and the installed version. What differs goes into `docs/harness-findings.md`.
- A step that deletes code deletes its tests and its UI in the same pull request, and says what a person can no longer do.
- The TypeScript mock and the e2e specs are kept in step by the step that changes a behaviour they cover.
- Schema changes are new steps at the end of `APP_STEPS` or `STEPS`. The harness has its own database and its own step list.
- The rules in `AGENTS.md` hold as G0 words them. A step that needs a rule changed stops and says so.
- No step merges to `main`, force-pushes, changes a provider login or a file in a login's config folder, or touches `~/Gossamr`.
- Under about 800 non-test lines added per step. Code that moves does not count.
- An acceptance line names a command and what it prints. "Looks right" is not one.
- Checks: `pnpm typecheck && pnpm test && pnpm build`, `mkdir -p dist && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace`, `pnpm e2e`. On this Mac `cargo` is at `/opt/homebrew/opt/rustup/bin`.

### H3. Harness: the API and the command line

- **Touches:** `crates/harness` (server, client module, CLI).
- **Does:** `harness serve` on a Unix socket in a folder only the user can open. The first client token is handed over at first start; `harness token new` needs a valid token. A client proves its token by answering a challenge. A descriptor with protocol number and build id. Requests: open a session, send a message, cancel, answer a permission request, answer a question, post a tool result, close, hand over (close the session as handed over to Terminal, keeping its provider id for a later resume), clean up, list sessions, list providers. Events over a WebSocket from a sequence number. A session option "ends when its client leaves". A Rust client, used by `harness sessions`, `events`, `send`, `answer` and later by the app. It also gets a `shutdown` that stops every session's task, or, for an agent that ignores Stop and Kill, gives up on it with a last `failed` and names its session, a sweep of old payload on a timer, and a path that loses no event for the client of a locked session, since the store cannot give those events back, within a memory bound (`LOCKED_BACKLOG` events and `LOCKED_BACKLOG_BYTES` of them): a client further behind on either is told that events were lost. H5c adds resuming through the client API (`resume`, with an optional "carry on") and taking a handed-over session back (`take_back`); H10 resumes after a restart, and H14 asks the person before a take-back. The sweep also deletes a session's event rows 30 days after it was cleaned up, and 90 days after its last event when it never was, so the table does not grow without bound, and the catch-up path does not run the sweep on every read. A running session keeps its rows; only their payload past 30 days is dropped.
- **Regression test:** no token, a wrong token and a session's tool token are refused on the client API. `token new` without a token is refused once one exists. The token is never sent on the socket (the test's fake server sees only the challenge answer). A client that reconnects with a sequence number gets exactly what it missed of what the store keeps; a locked session's events go only to a client connected when they happen, so one that reconnects gets its kept fields and not its text. A session that ends with its client is not resumed. `shutdown` stops every session's task and frees the data folder, and, for an agent that ignores Stop and Kill, says so, names its session and stops waiting for it; the sweep runs on its timer with no read or open; a locked session's client that falls behind, within `LOCKED_BACKLOG` events and `LOCKED_BACKLOG_BYTES`, misses no event, and one past either is told events were lost; a session cleaned up 31 days ago, and one never cleaned up whose last event is 91 days old, have no event rows left; a running session keeps its rows, even with its last event 91 days old; a catch-up read writes nothing.
- **Acceptance:** with `harness serve` running, `harness run --provider mock` from a second terminal streams the events of H2; after `kill -9` of that client, `harness events --after N` prints the rest; `harness answer` allows a mock permission request.
- **Rule:** a credential an agent can read without the person lets it approve its own requests. So the client token is never in an environment variable, an argv or a file: `serve` refuses to start while `HARNESS_TOKEN` is set and takes the first token on stdin. It reads a piped stdin to its first newline on every start and then puts `/dev/null` on fd 0, so no token waits in the pipe while it runs; a later token must be one the store already knows, or `serve` does not start, and the store keeps the tokens it has (H9). The CLI reads its token from stdin only (`--token-stdin`), piped from wherever the person keeps it. A Keychain item that trusts no app is a suggestion, not a promise that each read asks the person: check that it does. H9 settles where the app keeps its token. This does not stop a program of the same user that reads another process's memory or relays the socket (proposal section 8). The hello, the proof, its answer and `shutdown`, still behind the proof, keep their shape in every protocol (H9), so the app can stop a harness of another protocol without signalling a process it cannot prove is that harness.

### H5a. Harness: the tools endpoint

- **Touches:** `crates/harness`. Moves the transport, token and origin checks out of `agent/mcp.rs` the same way as H4a; the app's server keeps working on the moved code.
- **Does:** one MCP endpoint per session on loopback, with its own token stored as a hash and a per-session name drawn at random from a secure source, at least 64 bits, written in letters and digits only. What protects the allowance is that the name cannot be predicted: a person's server cannot be named to collide with it. `result` with an optional schema; `result` is refused while a question is open (H5b). The schema is a checked part of JSON Schema, and any other keyword is refused when the session opens: `type` (`object`, `array`, `string`, `number`, `integer`, `boolean`, `null`, or a list of them), `properties`, `required`, `additionalProperties` (a boolean or a schema), `items` (one schema), `enum`, `const`, `minLength`, `maxLength`, `minimum`, `maximum`, `minItems`, `maxItems`, with `title`, `description`, `default`, `examples`, `$schema` and `$comment` read as notes; its top level is `"type": "object"`. Pipeline steps (H20 to H22) write their schemas within it. Each `result` taken is an event, and the last one before the session ends counts. Tools the client declared: each call is an event the client answers; with no client it fails at once. A cap on calls per session. Calls to the session's own endpoint are allowed by the harness without asking the person, only for the exact full tool names built from the per-session name and never a prefix; each driver says how (H6 to H8), and nothing else is allowed that way. Each provider row names the setting that makes a tool call outwait a question, and its limit where none does. A resumed session gets a fresh token and the old one is refused. It adds the endpoint name, the declared tools and the result schema to `Open`, `Launch` and the sessions table, as a new migration step. Once the endpoint is on HTTP, the token is compared in constant time.
- **Regression test:** a session's token opens only its own tools and stops working when the session closes or is resumed. A request from a web page or another host is refused. A `result` that does not fit its schema goes back to the agent with the reason. The token is in no argv, log or event. An endpoint name comes from the secure random source with at least 64 bits, and has no `_` or `-`; a counter or a fixed prefix fails the test. A session's endpoint name, declared tools and result schema survive a restart; the token check uses a constant-time compare.
- **Acceptance:** `cargo test -p harness tools_endpoint` passes, and `harness run --provider mock --script <client-tool fixture>` prints the client-tool call event, then the answer the mock received.
- **Lands as** two pull requests: H5a-1, the move, the endpoint, the declared tools and store step 5; H5a-2, `result` and its schema check. Until H5a-2 merges, the `result` lines of Does and Regression test wait for it. The call cap is counted while the harness runs.

### H5b. Harness: `ask`

- **Touches:** `crates/harness`. Moves `runs/ask.rs` the same way as H4a.
- **Does:** `ask` is stored, survives a restart, blocks "carry on", and is answered through the API. Where a provider's limit on a tool call is below the wait, `ask` returns before the limit, measured from the call's start with a margin, with "question pending, end your turn". An answer whose call is no longer held (cut by that limit, or lost when the harness or the agent restarted) is sent as the next prompt on every provider, after the running turn ends, resuming the session first, with a fresh token, if it is not running. A second `ask` while one is open is refused with a message that names the open question. A question closes only when its answer is delivered: to the held call, or as a prompt actually sent, so an answer still waiting when the harness shuts down leaves it open. Every turn end lets a held `ask` call go with its question open. Stop, the hand-over request (H3, used by H14), clean-up, a resume refused for good, and a deny that ends the turn whose `ask` call is still held close open questions; a deny never closes one an earlier turn asked. The session says so in `question_closed`, before the turn's end. `sessions` names each session's open question. The mock provider has a tool-call limit and a resume (H2), so all of this is tested before the drivers exist.
- **Regression test:** one each: a question asked before a restart is still open after it, and its answer arrives as the next prompt after a resume with a new token; an `ask` on a mock with a 180 s limit returns before the limit; an answer that arrives while a turn runs waits for the turn to end; `result` is refused while a question is open; a second `ask` while one is open is refused, naming the open question; Stop and the hand-over request each close the open question and say so; a deny closes only the question whose call that turn holds, before `turn_ended`; an answer to a live session is sent with no resume; an answer waiting behind a turn at a shutdown leaves the question open; after a cancel, the answer is the next prompt. `ask`'s early return is measured from the call's start, not from the harness's own cut timer: a call that started 170 s before the session saw it still returns before a 180 s limit. Its tests drive the tool-call hold limit from a harness script: H2's fixture replay never replays a client tool call.
- **Acceptance:** `cargo test -p harness ask_` passes, and with `harness serve --mock-script <ask fixture>`, `harness run --provider mock --token-stdin` and `harness answer --token-stdin` from a second terminal, the run prints the question, "question pending", the turn's end, and the answer sent as the next prompt.

### H5c. Harness: resume and take back through the API

- **Touches:** `crates/harness`.
- **Does:** `resume { session, carry_on }` and `take_back { session }` on the client API, asked for by H10. Each waits for the connection's shell, starts the session again with a new tools token and watches it on that connection from its first event, so a locked session's client misses none. With `carry_on`, that text is the session's next prompt: checked under the start's lock, and again in the session's own step that queues it, so a question, a permission request, a stop or a hand-over that comes first means it is not sent, and the session says so in a `notice`. Refused, each with its own reason and no agent started: a session cleaned up, ended with its client, marked as one that cannot be resumed, handed over and not taken back (and `take_back` of one never handed over), whose worktree another session holds, or one a shutdown gave up on, whose agent may still run (#458 item 11; its clean-up is refused too). "Carry on" is refused while a question is open, and after a stop, a deny-ended turn, a cancelled turn or a permission request left open at the stop, a mark the next turn lifts. Store step 7 keeps the marks. A watch ends at a `closed` only when it is the last event read and the session is not live, so a resumed session's watch reads past the earlier start's `closed`.
- **Regression test:** one each: every refused resume, over the API too; each refused "carry on"; a question raised between the check and the send; a fresh token; take back, then resume; a deny or a cancel whose turn ends while the agent goes; a resumed locked session's carry-on turn reaching the client with no `watch`; a resume that waits for the shell; a watch of a resumed session from before its earlier `closed`.
- **Acceptance:** `cargo test -p harness --test resume` passes, and `harness resume <session> --carry-on <text>` resumes a session `harness serve` keeps.

### H6. Harness: the Claude driver

- **Touches:** `crates/harness`, and its fake `claude` in `crates/harness/test-support/` (moved from `src-tauri/test-support/`; the app's own run and Pip tests use the moved copy until H17 removes them). Moves the launch flags and stream parser of `claude/mod.rs` and `claude/stream.rs` with their flag tests; the app's Pip keeps working on the moved code. Adds the wire replay in `crates/harness/test-support/wire-replay`, which H7a, H7b and H8 reuse.
- **Does:** the native driver H0 decided for Claude: `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --permission-prompt-tool stdio`, with `initialize`, `interrupt` and `can_use_tool` on the control channel. The tools endpoint is given by the `mcp_set_servers` control request on stdin, with its header and a `timeout` above the `ask` wait, under its per-session name, so the token is in no argv and not in the agent's environment. The locked profile is today's flag list with the endpoint given the same way instead of `--mcp-config`, and with `--allowedTools` naming exactly `mcp__<name>__<tool>` for each of the session's own tools, like the normal profile, never today's `mcp__gossamr` prefix: under `--strict-mcp-config --tools ""` the session's `init` tools are exactly the endpoint's tools (H0, `r4-locked-control`), so both profiles use one route. The normal profile adds only that endpoint, `--allowedTools` with exactly `mcp__<name>__<tool>` for each of its tools, the guard and a model. The guard says never to turn off commit signing or hooks, and to report it. Resumes after a restart wait for the first shell capture: until one has worked, the harness refuses to start any agent, a resume included, and never runs one in its own environment (H4b, `Setup::agent_env`), so this step captures the shell at start, before it resumes sessions. Leftovers of a dead harness are stopped at start, by pid and start time: an orphaned `claude` outlives its client and ends its turn alone. Resume by id with the "carry on" rule, never after a turn that a deny ended, with a fresh token. Turns are counted by `result`, not by prompt: one prompt can give two `result`s when Claude starts a turn by itself after a background workflow ends, and the turn limit and "carry on" use that count. Events after `result` are accepted, and Stop also stops background tasks. It sends a usage event for each turn, and a "permission closed" event when Claude withdraws a `can_use_tool` request. It passes an effort (`--effort`) beside the model, only when the person chose one other than the default; this is the first step that passes one, so the rule-4 wording in `AGENTS.md` gains "and effort" here: an agent gets a model and an effort only when the person chose one other than the default, and nothing else. Its migration step stores the agent's pid and start time per start, so a new harness can stop a leftover `claude` and a stuck session can be ended after a restart. H6 builds the wire replay: a fake CLI that plays a fixture's `from_agent` lines over stdio, with the recording's ids mapped to the run's, and checks each line the driver sends against the recorded `to_agent` line on the fields a replay needs: the method or type, the ids by that mapping, a prompt's text, a permission's decision, and a cancel. The per-session server name, the token header, the `initialize` capabilities and the config lines the driver chooses to send are not compared. A driver run against it is compared with H2's converter on the projection H2's golden files hold: event types in order, permission kinds and decisions, tool names, ids compared by position, turn ends and failures, and text lengths, on the fixtures each entry names. A difference is settled by reading the transcript, never by taking either side as right. What a driver adds on purpose (usage and warning events, `r1-collision` as a failed turn) gets assertions of its own and is left out of the comparison.
- **Regression test:** against the wire replay of the fixtures each entry names (here `claude/native`), the driver gives the same projected events (H6) as H2's converter gives for each (the two are written apart, so a rule wrong in one shows as a difference); against the fake Claude: the exact argv of both profiles; no restricting flag in the normal one; a restart in the middle of a turn resumes once; a restart with an open question sends no "carry on"; a reused pid is never signalled. `--allowedTools` names exactly the endpoint's tools; a second server's tool and a colliding name (server `a_b` with tool `c` beside server `a` with tool `b_c`) are not allowed by the driver. The endpoint is sent by `mcp_set_servers` in both profiles, and the token is in no argv and no environment variable of the child. No "carry on" after a deny-ended turn. A resumed session gets a new token. Two `result`s from one prompt count as two turns. On the locked profile a call to one of the session's own tools is not denied, and `--allowedTools` holds no prefix rule. A `result`'s usage becomes a usage event; a withdrawn `can_use_tool` closes its permission id, and a later answer to it is refused. ## Flagged concerns

- **H0 can change the plan.** Entries H6 to H8 name "the driver H0 decided"; H0 decided them, and the entries now say which. Their briefs are written after H0.
- **Automatic merging is never exercised for real.** It is tested against the fake GitHub only. This repo's review bot never approves, and the scratch repo has none. The first real use is the owner's, and the first wave in a repo waits for the owner anyway.
- **Same user.** Agents run as the owner, like the harness. The controls stop accidents and simple injection, not a program that sets out to read the harness's store (proposal section 8).
- **Provider terms** are the owner's decision (proposal section 8).
- **One GitHub account.** Landing is checked in code, but an agent can still call `gh`. Branch protection and a second account are the owner's to set up.
- **Stage 2 of pipelines** (P1, H21, H22) is the largest and least certain part. It is built last and can be left out without touching the rest.
- **The window** is checked by building and starting the app and by tests on the page, not by a person's eye.
- **H20 needs a scratch GitHub repo.** The orchestrator asks before creating one.
- **Sessions can only be started on a turn the owner began, or one that follows a finished session.** If that chain breaks, the orchestrator needs one word from the owner to go on.
