Two things about the setup itself:

- **Agents must not inherit a Claude Code session's variables.** The first Claude runs, started from inside this Claude Code session, carried `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_ENTRYPOINT=claude-desktop`, a messaging token and account ids into the child `claude` (its MCP user agent read `claude-desktop`, and it emitted `post_turn_summary` and `task_summary` events that a clean run does not). The driver now removes `CLAUDE*`, `ANTHROPIC_*`, `MCP_*`, `AI_AGENT`, `CODEX_*` and `OPENAI_*` before it starts an agent, and every Claude fixture was run again that way (user agent `claude-code/2.1.330 (sdk-cli)`). The harness, started by the app, must build an agent's environment from the person's shell the same way, never from its own.
- **Since H6b the shell is captured from a cleared environment** (`crates/harness/src/env.rs`). `$SHELL -ilc env` starts with only `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `LC_*`, `SSH_AUTH_SOCK`, `__CF_USER_TEXT_ENCODING`, the proxy and CA variables (`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `ALL_PROXY` and their lower-case forms, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`) and the system PATH. So nothing else the harness or the app inherited reaches an agent, a Claude Code session's variables included, and what the person's start files set does. The app shares this capture, so this changes what Pip and the app's agents get: started from a terminal, they no longer get that terminal's one-off exports; started from Finder, **a variable set only with `launchctl setenv` and in no start file no longer reaches them**, except the proxy and CA variables above.
- **The CLIs write their own per-session state on the real login.** That is not avoidable on a real run and was not removed, since removing it writes to those folders: `~/.claude/projects/<cwd as a path>/<session>.jsonl` and shell snapshots; `~/.codex/sessions/2026/11/22/rollout-*.jsonl` (66 files), its SQLite files, `shell_snapshots/` and `session_index.jsonl`; `~/.gemini/antigravity-cli/conversations/<session id>.db` (a SQLite file of about 450 KB per session) and logs. `codex delete --force <thread>` and `claude purge <path>` remove a session's files.

## A write into a login folder (Codex)

`codex app-server` 0.171.0 writes project trust into `$CODEX_HOME/config.toml` when a thread is started with a sandbox: the `sandbox` field of `thread/start`, or a `sandbox_mode` config override. In check 2 it created `~/.codex/config.toml` holding `[projects."$SCRATCH/clone"] trust_level = "trusted"`. The file did not exist before and held only that entry; it was removed. `spikes/acp/scripts/codex-trust-probe.sh` reproduces it in empty scratch homes. A sandbox on `turn/start` (`sandboxPolicy`), `exec -s` and every ACP mode do not write it. **The Codex driver must never pass a sandbox on `thread/start`.** H7a rechecked it on 0.171.0 (`codex_real`, 26 Nov 2026), in an empty signed-out `CODEX_HOME` and a worktree of a clone: the driver's own `thread/start`, with no sandbox, wrote no `config.toml`, and the same request with `"sandbox": "workspace-write"` wrote one. In a plain folder that is not a repository neither wrote one, since trust is kept per repository root, so the check must run in a clone. Two fixtures (`codex/{exec,app-server}/2-permission-escalate`) ran while that entry existed and do not show the person's default.

## Where the docs and the binaries differ

- **Claude** `--permission-prompt-tool` is not in `claude --help` 2.1.330, though `--permission-prompts` names it and it works (`stdio` sends `can_use_tool` on stdout). `--restricted`, `--safe-mode` and `--bare` are new since the findings in `agents-cli-findings.md`; none was used. A foreground `sleep N` is refused by the CLI itself, and long commands are moved to background tasks on the model's choice; neither is in the headless docs.
- **Claude ACP**: the docs present the adapter as a way to run Claude Code; the code shows it runs the Agent SDK's bundled CLI unless `CLAUDE_CODE_EXECUTABLE` is set, and passes its own permission mode and tool flags.
- **Codex**: the app-server README says `item/commandExecution/requestApproval` comes for a "managed requirements.toml prefix rule with decision prompt-user"; in 0.171.0 it came for every command under approval `untrusted`, and for an escalation under `on-request`. `exec` refuses `approval_policy="untrusted"` ("no longer supported"), which app-server still takes. `item/tool/call` (client-declared tools) is in the schema, but `ThreadStartParams` has no field to declare them.
- **agy**: the headless docs show stream-json without `-p`; `-p` before `--input-format` is refused. `agy acp --help` lists `--login`, `--gemini-dir`, `--app-data-dir` and `--process-per-session`, which the ACP page does not describe. No `mcpCapabilities` in `initialize`, yet `session/new` takes an HTTP MCP server and uses it. The headless docs say an action that needs approval is soft-denied; in the stream runs edits and `ls` ran unasked (`permission_mode: request-review`). `--mode auto` is refused for the owner's account type.
- **ACP**: the agents speak protocol v1 with `session/load` and the unstable `session/resume`; the v2 migration (`session/resume` with `replayFrom`) is not offered by any of them.

### What each driver must do

- **Claude.**
  - Build the environment from the person's shell, never the harness's own: drop `CLAUDE*`, `ANTHROPIC_*` and the like.
  - Give the tools endpoint by the `mcp_set_servers` control request in both profiles, under a per-session random name (at least 64 bits, letters and digits only), with its header and a `timeout` above the `ask` wait (the default cuts at 60 s), and pass `--allowedTools` with exactly `mcp__<name>__<tool>` for each of its tools, in the locked profile too (never today's `mcp__gossamr` prefix).
  - Count turns by `result`, not by prompt.
  - On a harness restart, stop the orphaned `claude` by pid and start time first: it outlives its client and ends its turn alone. Resume with a fresh token; the old one is refused.
  - Accept events after `result` (a background task's notice) and a turn the agent starts by itself after a background workflow ends. Stop also stops background tasks: with one running, `claude` does not exit on stdin EOF.
  - Check the locked session's `init` tools before answering any tool call; `init` arrives after the first user message.
- **Codex.**
  - One app-server process per session, so Stop can stop the process tree: `turn/interrupt` leaves a running command alive.
  - Check the version and the shape of `initialize` at start; never set `experimentalApi`; ignore unknown notifications.
  - Never pass `sandbox` on `thread/start` or a `sandbox_mode` override (app-server then writes trust into the person's `config.toml`). Pass no approval policy or sandbox at all.
  - The endpoint in `config.mcp_servers` under a per-session name, with the token in `http_headers`, `tool_timeout_sec = 600` and `default_tools_approval_mode = "approve"` on that one server key. Another server's tool asks through `mcpServer/elicitation/request`.
  - Check the protocol's shape at start (`scripts/codex-recheck.sh --shape-only` is the same check by hand); an untested version is a warning, not a block.
  - Answer all three approval kinds: `decision` for commands and file changes, a granted profile and scope for permissions. An escalation request goes to Needs you; a run that ends blocked says so.
  - A restart resumes by thread id with a fresh token; the cut turn is lost.
  - A thread's `config.mcp_servers` adds to the person's own servers: on 0.171.0, a thread started with `{"mcp_servers": {"<name>": …}}` in a `CODEX_HOME` whose `config.toml` holds `[mcp_servers.mine]` lists both `<name>` and `mine` (`mcpServerStatus/list`), as does the dotted key `"mcp_servers.<name>"` (H7a, 26 Nov 2026, in an empty signed-out scratch home).
  - Codex can start a command in a process group of its own, which a kill of app-server's group does not reach. The H7a driver notes app-server's process tree every second and at each `item/started`, and on any end kills each noted process and the group each led, so what an exited command left in its group goes too. The session keeps the noted tree on record beside app-server, each process by pid and start time (H7a-2). The next harness kills a stored process only while its pid has its start time, with the group it leads; for one that has exited, only the members of its group that `left_of` takes for a dead agent's, and with any other member the session stays given up on. A stored pid can be hours old and lead the person's own group by then.
  - A job a command sends to the background in the command's own group is gone by the turn's end: on 0.171.0, in Codex's default sandbox, a turn whose command was `sleep 300 > /dev/null 2>&1 & echo $!` said the job's pid, and no `sleep 300` ran anywhere once the turn ended, twice (`codex_real_a_job_a_command_sends_to_the_background_is_gone_by_the_turns_end`, 27 Nov 2026). Codex ends the command's group when the command returns. With another sandbox setting this is not checked.
  - A job that leaves that group too, by `setsid` say, and whose shell exits before a note sees it, is in no tree or group the driver noted. Once its shell exits, the system takes it in (launchd or init, on Linux app-server as a subreaper). So at a session's end and at a restart, the harness also kills every process of yours that started at or after the agent, works inside the session's worktree and carries the session's mark, whatever its parent is now, parents before their children so a supervisor cannot restart one, each by pid and start time, and lists them a second time for what forked meanwhile; a session that names no repo has no worktree, and nothing is taken for it. Whoever its parent is: the system takes in only the job itself, and what the job started is the job's child. The mark is `GOSSAMR_SESSION=<session id>` in the agent's environment, which Claude and Codex pass to the commands they run. Without it, a job you started in a Terminal opened in the worktree and then closed, or an editor started from there, would pass the start and folder checks too. The environment is read with `KERN_PROCARGS2` on macOS and `/proc/<pid>/environ` on Linux, only for your own processes.
  - What the mark misses. A command that clears its environment (`env -i`, or a program that starts its children with a fresh one) leaves no mark and is not found, nor is what it starts. Codex's `shell_environment_policy` can drop the mark for every command: with `inherit = "core"` or `"none"`, or an `include_only` list that does not name `GOSSAMR_SESSION`, its commands start without it (from Codex's config options; not run here). On macOS 26.7, Apple's own programs (`/bin/sleep`, `/bin/sh`, `/bin/zsh`, `/usr/bin/perl`) do not show their environment to another process: `KERN_PROCARGS2` gives their arguments only, so a process that runs one is not found. `node` from nvm (hardened runtime) and Homebrew's `python3` show theirs. So for `npm run dev &`, `npm` and the server it starts are both found, since both are `node`; a shell between them, as `npm` runs scripts through `sh`, is not, and one that only waited on them exits once they have; a loop or a supervisor among those not found (`while :; do npm run dev; done`) starts the killed process again. The environment rule was seen on 27 Nov 2026; `npm run dev &` itself was not run here.
  - What the mark takes that may be yours. Whatever the agent starts carries the mark, so a server it starts that outlives the command ends with its session, and so does what you run through it. If the agent runs `tmux new -d -s dev` with no tmux server running, the server starts with the session's environment. A window you open after attaching to it from a Terminal gets the server's environment and, opened from the worktree, works there, so its shell and what you run in it are killed at the session's end. Claude's background daemon may be another: the first `claude --bg` for a config folder starts it, so if an agent runs one, the daemon carries the mark, and so does every background session it runs later. It is taken only if its working folder is inside the worktree, and those sessions only if they work there too; not checked, since no daemon ran here (`lsof -a -p <pid> -d cwd` shows its folder). Taking a marked process only when the agent started it would mean noting the session's own servers, which this design avoids.
  - What noting still cannot reach: a process that leaves app-server's tree after the last note and works outside the worktree, or that a subreaper above the harness took in. On Linux, app-server runs as a child subreaper (`PR_SET_CHILD_SUBREAPER`), so what its commands orphan stays in its tree while it runs; what app-server has not reaped stays a zombie until it exits. macOS has no subreaper.
- **Claude, the same gap (H7a-2).** Claude Code 2.1.328 starts each Bash command's shell in a process group of its own: the shell's group id is its own pid, not `claude`'s, and a command the shell sends to the background stays in the shell's group. The Claude driver kills `claude`'s group on Kill and notes no tree, so a command running when `claude` is killed outlives it, and once `claude` has exited at a restart nothing on record leads to it. At a restart with `claude` still alive, its descendants are killed with it. The session's own check for marked processes inside its worktree, at its end and at a restart, reaches a Claude session that names a repo too, since `claude` gets the session's mark. On macOS, what a Claude session's end leaves is each shell `claude` started (`zsh`, one of Apple's programs, whose environment is hidden, see above) and any of Apple's programs it still runs, such as `sleep` or `/usr/bin/python3`; each marked program of another maker under it, such as `node` from `npm run dev`, is killed, and a shell that only waited on it then exits, but a shell that runs it in a loop, or a supervisor that cleared its environment or works outside the worktree, starts it again. On Linux each shell inside the worktree is found too. What works outside the worktree, or runs for a session that names no repo, is not found on either. Seen from this machine's own Claude Code shell (`ps -o pid,ppid,pgid`), 27 Nov 2026.
- **Gemini.**
  - The endpoint in `session/new` and `session/load` `mcpServers` with the token in `headers`; a workspace `.agents/mcp_config.json` is not offered to the model in an untrusted workspace.
  - Give the endpoint a per-session random name (at least 64 bits, letters and digits only), and answer `allow_once` by itself only when the request's `name` is exactly `mcp_<name>_<tool>` for one of its tools, never by prefix. A person's server whose tool name collides makes agy refuse the session (R1).
  - A turn can end (`end_turn`) while a command agy started still runs: track agy's descendants after `end_turn`, do not report the run finished while one runs, accept the message agy then sends by itself, and stop the process tree on Stop.
  - A deny ends agy's turn with no reply: no "carry on" after it, and the run reads "stopped after a deny".
  - MCP calls are cut at 180 s with no setting on this path, so `ask` returns early and the answer comes as the next prompt.
  - Stop stops the process tree, and does not wait for `agy acp` to exit promptly while a command runs.
  - agy keeps the MCP header, token included, in its conversation database: the token must stop working when the session ends.
  - Feature-detect HTTP MCP (no `mcpCapabilities`) and agy's own `tool_call` fields (`name`, `args`, snake_case copies). Answer GET requests without the Authorization header with 401 and do not count them as abuse. (H5a: the harness's endpoint answers every GET with 405, as MCP 2025-06-18 asks of a server with no event stream, whatever the header; H8 checks that agy goes on after a 405 as it did after the spike's 401.)
- **All providers.** A commit the person's signing agent refuses fails unattended. Claude, Gemini and Codex on app-server reported it; Codex on exec and ACP turned signing or hooks off by themselves. The guard says never to do that.
